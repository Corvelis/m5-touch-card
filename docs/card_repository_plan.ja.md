# 名刺交換製品 — 別リポジトリへの引き継ぎ計画

以下は設計時の切り出し計画（経緯として保持）です。独立リポジトリへの移植は実施済みで、
この文書の予定構成・未着手表現は現在の作業状況を示すものではありません。
現在の構成・検査結果・実機未検証事項は[実装状況](implementation_status.ja.md)を参照。
設計時の製品要件は[名刺交換ファームウェア仕様案](card_firmware_spec.ja.md)、現在の使い方は[操作ガイド](operation.ja.md)を参照。
この文書はリポジトリ構成、再利用範囲、保存処理の責務、検証順を定める。
既存のPaper Mono画像転送製品のコード・配布物・ワイヤ仕様を変更しない。

## 1. 別リポジトリの境界

- 新製品のファームウェアとAndroid/iPhone共通アプリを1つのリポジトリで管理する。
  リポジトリ名・公開範囲・所有者・アプリID・署名は作成時に決める。
- Paper Mono用とNFC対応Stack-chan用に別のビルドターゲットを持つ。名刺モデル、
  NFCアプリケーションプロトコル、保存・削除・索引の処理は共通化する。
- 端末別の表示、ボタン、RTC、電源、SDとNFCの初期化はハードウェア層に閉じ込める。
- 最初のStack-chan対象は公式K151/K151-R。自作・別コアは個別のボード対応が必要。
  顔や会話機能のある既存ファームウェアへの組み込み口を設けるが、その既存機能全体の
  移植・置換やクラウド接続を初期版の必須要件にしない。
- 今のリポジトリはC153専用の既存製品として維持する。現在の17画像保存、歩数、
  プロトコルv1はこの計画によって変更しない。

│  ├─ src/boards/stackchan/           # 横画面・RTC・NFC・SD・既存機能との接続
│  ├─ src/storage/                   # LittleFS / SD のアダプター
│  ├─ assets/                        # 日本語フォント、独立した3用途の初期画像

## 3. 既存実装の再利用と作り直す部分

| 現在の実装 | 新製品での扱い |
| --- | --- |
| `firmware/src/PaperMonoNfcProtocol.h`と`protocol/` | フレーム検証・CRC・分割転送の参考。名刺対応のワイヤ仕様は別に定義 |
| `firmware/src/PaperMonoNfcController.cpp` | NFC-A受信、再開、保存通知を分離して再利用。17枚固定・最古の自動削除は引き継がない |
| `firmware/scripts/patch_m5unit_nfc.py` | ピン留めした依存とともに監査・移植。リーダー側も別途実機検証 |
| `firmware/src/RtcClock.*` | UTC/オフセットの考え方を再利用。機種別RTCへ分離 |
| `firmware/src/DashboardView.*` | 大きい時計と週間表示の構成を参考に再描画。歩数処理は移植しない |
| `mobile/lib/core/image/`と画像編集処理 | 選択・切り抜き・JPEG検証を再利用し、3用途と機種ごとのサイズへ拡張 |
| `mobile/lib/features/transfer/`とAndroid/iOSのNFC実装 | NFCの既知の再試行・中断処理を移植し、更新対象と新しい能力確認を追加 |
| `mobile/lib/app.dart` | 画面を名刺/画像の2タブへ再構成。開発用CRC等を通常画面へ常時出さない |
| テスト、ライセンス表示、初期画像 | 必要部分を移植し、出典・著作権・依存の通知を保持 |

ビルド成果物、`.pio`、端末に保存した実名刺、署名情報、個人設定はコピーしない。
初期画像の権利表記は`firmware/assets/LICENSE.md`も引き継ぐ。

既存の`AppController.cpp`は`LittleFS.begin(true)`を使うが、新製品はマウント失敗時に
利用者の名刺を自動初期化しない。未初期化媒体と破損・認識失敗を区別し、復旧や初期化は
明示操作として別設計にする。現在の動作はこの整理の中では書き換えない。

## 4. 保存サービスの分離

| 層 | 責務 |
| --- | --- |
| `CardRepository` | プロフィールID・更新世代、同一IDの表示統合、ページ取得、削除ユースケース |
| `StorageRouter` | 自動/本体の設定、媒体状態、受信前の保存先選択、転送中の保存先固定 |
| `StorageBackend` | 読む、作業世代を書く、検証、公開、削除、容量取得、同期、復旧 |
| `InternalBackend` | LittleFS上のアプリ領域。自分の名刺と画像用領域を確保 |
| `SdBackend` | SD上の専用領域。取り外し、書込不可、I/O失敗を区別 |
| `StorageUsageService` | 媒体全体の使用量/空き容量と、アプリ・名刺・作業領域の内訳 |
| ボード層 | SD/NFCの電源、バス、挿入検知、初期化、表示とのアクセス調停 |

受信名刺の保存先は「自動（SD優先） / 本体」。自分の名刺・アイコン・2画像・設定は
内部に保持する。SD上のすべてを内部へミラーせず、SD容量が内部容量に縛られない構成に
する。初期版に既存名刺の一括移動・バックアップ・SD全体のフォーマットは含めない。
実装時に保存先規則を簡略化した。自動設定では既存コピーの場所によらずSDを優先し、
本体指定時は本体へ保存する。BEGIN時点で保存先を固定し、表示時は同一IDを統合する。

### 媒体と索引

- 内部とSDは別ボリュームで管理し、合計容量を1つの連続した書き込み領域とみなさない。
- SDごとの識別子とマウント世代を使う。抜去後に別のSDが挿された場合、古い
  ファイルハンドル・再開情報・キャッシュで別媒体へ書かない。
- SDにカード数比例の索引を保持する。NVSや内部フラッシュにSD全件の索引を必須で
  複製しない。NVSには設定・小さい管理値、RAMには表示ページと上限付きキャッシュを
  持ち、大容量SDの名刺帳を全件メモリへロードしない。
- 接続中の媒体の索引を統合して名前順/受信順でページ取得する。プロフィールIDの
  重複は新しい更新世代を優先する。名前の読み、同世代の競合、受信順のタイブレークを
  データ仕様で固定する。同世代で内容が異なる場合は無言で上書きしない。
- 起動/挿入時のスキャンは段階的に行い、読込中を示す。索引破損時に専用領域の
  正常レコードから再構築できるようにする。SDの無関係なディレクトリは読まない。
- 名前やメールをファイル名へ直接使わず、検証済みIDで格納する。SD上の外部変更を
  信用せず、パス、スキーマ、文字長、画像寸法、チェックサムを検証する。

### 容量判定

容量・バイト数は64ビットで扱う。各媒体について次の値を区別する。

```text
媒体の空き容量 = ファイルシステムが報告する空き容量
名刺に使える容量 = max(0, 媒体の空き容量 − 常設予約領域)
受信に必要な容量 = 新世代の本文/画像 + 索引/管理情報 + 転送固有の作業量
```

- 常設予約領域は、自分の名刺・ホーム画像の将来の更新余地と復旧・管理処理に必要な
  空きを含める。転送固有の作業量をここへ二重に計上しない。
- 新規だけでなく更新でも、新世代を検証し終わるまで旧世代を保持するための空きを
  見込む。ファイルシステムの割当単位・索引の拡張・管理オーバーヘッドも考慮する。
- 受信開始前に予約し、書き込み時にも容量/I/O失敗を扱う。他のStack-chan機能による
  ファイル増加で事前判定後に空き容量が変わる可能性を考慮する。
- 受信・削除・再マウント後に実測を更新する。ファイル長の合計を媒体全体の使用量と
  同一視せず、SDの他アプリ使用量も総使用量に含める。
- 件数は実際の索引から示し、「○件分空き」を正確値として表示しない。保存形式や
  管理データ量の上限に先に達したら、容量不足とは別の理由を表示する。

現行の内部領域は`firmware/partitions_16mb_ota_4m_littlefs_7m.csv`のデータパーティション
`0x7E0000`バイトであり、16 MB Flash全体ではない。新製品ではフォント・2ターゲット・
アプリ領域のサイズから再設計し、予約サイズを含めて実機で確定する。古い分割を無条件に
採用したり、初期表示へ固定の容量値を埋め込んだりしない。

### 更新・復旧・削除

- NFCの受信コールバックは検証・コピー・応答に限定し、SD走査・容量計算・画像描画・
  同期書き込みを直接実行しない。保存処理はキュー化し、RF応答を妨げない。
- 転送ID、更新対象、ボリュームID、マウント世代を対応づける。メディアが変わった
  転送を別媒体で再開しない。受信途中でSDが外れたら中断し、再試行で保存先を再選択。
- データを作業世代へ保存し、長さ・CRC・形式を検証し、公開する世代と索引を確定した
  あとで保存完了を通知する。SD/FAT上のrenameだけを電源断に対する原子性とみなさず、
  世代付き管理情報・検証済み状態・起動時復旧を設計して故障注入で確認する。
- 削除は対象IDと現在接続中の保存先を確定してから行う。完了済み削除が索引再構築で
  復活しないよう、削除意図と処理段階を残し、本文・アイコン・索引を整合させる。
  削除記録の整理は残存ファイルと整合が取れてから行う。
- 接続中の複数コピーの削除は単一の原子的トランザクションと仮定しない。片方が
  読取専用・抜去・I/O失敗なら残っているコピーと未完了を表示し、再試行できるようにする。
  未接続SDへの削除予約はしない。復元不可の注意は通常アプリ操作についてであり、
  SDの物理的な完全消去を意味しない。
- 安全な取り外しは書込開始を止め、進行中処理を完了/キャンセルし、同期・クローズ・
  アンマウントして完了する。再マウントは明示的な再読み込み・再挿入・再起動まで抑止する。
- FAT等の媒体全体の破損やSDコントローラ内部の電源断挙動はアプリだけで完全には
  防げない。正常な旧データを優先して復旧し、読めない媒体を勝手に初期化しない。

## 5. NFCとスマホ側への引き継ぎ

- 共通の「スマホから更新」待機へ、名刺本文/アイコン/日時用画像/全画面画像/時計を
  明示した要求を送る。画像寸法から保存先を推測しない。
- `HELLO`相当の能力確認に、バージョン、機種、更新対象、形式・寸法・最大データ量、
  保存可否・必要なら保存先状態を含める。具体的なフィールドは新ワイヤ仕様で確定する。
- 構造化名刺やカード交換用セッションを既存v1の画像モードへ無理に混在させない。
  対応外の既存ファームウェアには送らず、分かるエラーを表示する。
- スマホは名刺・日時用画像・全画面画像とそれぞれの切り抜きを独立保存する。
  未完了送信は対象と機種と内容を関連づけ、別画像の操作で無言に上書きしない。
- 送信前の本体保存先表示、容量不足・SD抜去・書込失敗・保存完了の文言を両OSで揃える。
- C++/Dart/Kotlin/Swiftで共通のテストベクトルを使う。フレーム仕様とデータスキーマは
  リポジトリ内に1つの正本を置き、ネイティブ層への複製は検査する。

## 6. 実装順と完了条件

| 段階 | 実装範囲 | 完了の目安 |
| --- | --- | --- |
| 1 | リポジトリ骨組み・名刺モデル・新通信仕様 | 両ターゲットの最小ビルド、共通ベクトル、失敗時の仕様が揃う |
| 2 | Paper Mono内部保存・スマホ編集/更新・3画像・時計 | SDなしで作成→更新→表示→再起動が通る |
| 3 | 受信名刺帳・容量UI・削除・復旧 | 容量不足と削除でデータを壊さず、使用量を確認できる |
| 4 | microSDバックエンド・保存先・統合索引 | 未装着/装着/抜去/満杯/読取専用/破損時の動作が通る |
| 5 | 機器間NFCリーダー送信・Stack-chan統合 | Paper↔Paper、Paper↔Stack、Stack↔Stackの両向き送受信を実機検証 |
| 6 | 仕上げ・配布 | 両画面の3デザイン、日本語・長文・QR、Android/iPhone、電源・SD条件を検証 |

段階1〜2で、SDのマウント/容量取得と機器間NFCの最小通信も並行して技術検証する。
後工程までハードウェア上の成立性を先送りしない。「双方向を検証」は片方向の送受信を
双方の役割で試す意味であり、1タッチの相互交換を初期版の完成条件に追加しない。

### 必須の保存テスト

1. SDなし、本体のみ指定、空の利用可能SD、他ファイル入りSD、満杯、読取専用、認識失敗。
2. 3用途の画像独立性、自分の名刺保持、内部予約領域、最大級名刺と索引拡張の容量判定。
3. 保存の各段階で中断/電源断/SD抜去。誤った成功通知・別媒体への書き継ぎがないこと。
4. 同一IDを内部/SDへ別々に受信し、再挿入・新版/旧版・同世代競合で適切に表示すること。
5. 削除のキャンセル、単一コピー、複数コピー、部分失敗、再起動、空き容量の回復。
6. SD-AからSD-Bへの交換、未接続コピーの再出現、索引再構築、外部変更された不正データ。
7. 大量名刺のページ表示・名前順/最新順・索引再構築で、内部フラッシュ/RAMを全件分使わないこと。
8. 安全な取り外し、再読み込み、SDがなくても名刺を渡せること。他アプリのファイルを変更しないこと。

容量、書込速度、書込時消費電力、対応フォーマット、NFC所要時間、実用上の件数は
測定結果を残して公開する。仕様文書だけで実機対応完了とはしない。

## 確認したハードウェア資料

2026-09-05に公式資料を確認。

- [Paper Mono C153](https://docs.m5stack.com/en/core/PaperMono): microSDスロットあり。
  SD用信号とIOエキスパンダー経由の電源/挿入検知が記載されている。
- [StackChan K151/K151-R](https://docs.m5stack.com/en/StackChan): microSDスロットあり。
  実装はそのメインコントローラーのピン・電源構成を使い、Paper Monoの初期化を流用しない。

スロットの搭載確認と、この新ファームウェアでのSD・ファイルシステム動作検証は別。
この時点では新ファームウェアのSD動作、抜去時の復旧、フォーマット別の互換性は未検証。
